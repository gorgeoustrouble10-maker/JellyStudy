## 三、优点（值得写进答辩/简历的）

### 3.1 架构与设计

1. **服务边界清晰**  
   - 知识点 8081 / 问答 8082 / 评估 8083  
   - 业务库 `jellystudy` 与评估库 `jellystudy_evaluate` 分离，符合微服务「各管各的数据」。

2. **Redis 不是摆设**  
   - 热门/常看走 ZSET + 详情 STRING，评估走读缓存 STRING。  
   - **写穿 + 启动预热 + 定时全量同步 + 空榜兜底**，四层策略在报告 §五 写清楚，答辩时能讲「为什么不用纯 Cache-Aside」。

3. **浏览量以 MySQL 为准**  
   `QuestionServiceImpl.getById()` 先 `incrementViewCount` 再 `onQuestionViewed()`——这是正确工程直觉，避免纯 Redis 计数丢失。

4. **Dubbo 用法规范**  
   HTTP 进本地 `*ServiceImpl`，跨服务走 `@DubboReference`；异步评估抽成 `EvaluateAsyncExecutor`，避免 `@Async` 自调用陷阱。`docs/DUBBO_ARCHITECTURE.md` 有约定。

5. **大模型可降级**  
   `ModelEngineSelectorConfiguration`：有效 `sk-...` + `qianwen` 才走千问，否则 Mock；SkyWalking Trace 能证明真实调用链（~2s + MySQL + Redis SETEX）。

### 3.2 工程与体验

6. **前端完成度高**  
   Vue 3 + Tailwind，Hash 路由刷新不丢页，侧栏三服务探活，「热门/常看」Tab 与 Redis 后端对齐。

7. **运维脚本齐全**  
   Docker Compose 一键基础设施、`start-java-services.ps1`、打包脚本、截图指南、时序图渲染脚本——**比多数同学项目更「能跑起来」**。

8. **文档分层**  
   实验报告（交作业）+ RUN_GUIDE（跑起来）+ REDIS_READ_BEHAVIOR（行为说明）+ SECURITY（生产注意）——角色分工明确。

9. **安全意识有雏形**  
   `local-secrets.bat` gitignore、prod profile 关 Swagger、可选 API Key、`docs/SECURITY.md`——课程项目里不多见。

### 3.3 代码可读性

10. **Redis 逻辑集中**  
    `QuestionRedisService`、`EvaluationRedisCache` 命名直观，配置外置到 `application.yml` 的 `jellystudy.redis.*`，改 key/TTL 不用改业务代码。

## 四、缺点与风险（知无不言）

### 4.1 高优先级

| 问题 | 说明 | 影响 |
|------|------|------|
| **密钥暴露风险** | `local-secrets.bat` 含真实 DashScope Key | 若 zip/聊天/截图泄露，需立即轮换 |
| **测试极少** | 全项目仅 **5** 个 Java 测试类，无 Redis/Dubbo 集成测试，前端零测试 | 改代码易回归，答辩被问「怎么保证 Redis 同步正确」较被动 |
| **报告 §4.2 与代码略不一致** | 报告写常看榜 score=累计浏览量；代码 `computeViewRankScore` 也乘 **7 天衰减** | 口试可能被追问，需统一口径 |

### 4.2 中优先级

| 问题 | 说明 |
|------|------|
| **README 过时** | 仍写 Zipkin :9411、前端 :5173，与现栈（SkyWalking :8090、:9945）不符 |
| **API 响应不统一** | 三模块各有一套 `ApiResponse`；评估 POST 裸 DTO，GET 包一层——前端到处 `data.data \|\| data` |
| **问题 update 不同步 Redis** | 改标题/内容后 `jelly:question:{id}` 可能 stale，直到下次浏览或 5min 同步 |
| **点赞 API 无前端** | `POST /questions/{id}/like` 存在但 UI 无入口，热门榜主要靠浏览/回答驱动 |
| **删除链路重复** | 前端删问题再调评估 DELETE，后端 Dubbo 已级联——冗余，偶发部分失败难排查 |
| **LLM 失败不落库** | `createFallbackQuestionEvaluation` 只返回 DTO，不写 MySQL/Redis，用户可能「提交了但评估页空」 |
| **健康检查偏浅** | `/api/health` 只返回 UP，不探测 Redis/MySQL/Nacos |
| **5min 全表 `findAll()` 同步** | 数据量大时 O(n) 全量 rebuild，无增量/消息驱动失效 |

### 4.3 低优先级 / 技术债

- 父 POM 残留 MongoDB 依赖（模块里 exclude 了）  
- 无 API Gateway / BFF，生产需 Nginx 或 Spring Cloud Gateway  
- Java 服务未 Docker 化，无 CI/CD  
- IDE 485 个 Lombok 红点：Maven 能编过，但影响开发体验  
- Windows 脚本为主，Linux/mac 同学需自己适配

3. 补 3～5 个 **Testcontainers Redis** 集成测试（hot/recommended/getById/eval cache）  
4. 问题 `update()` 后调用 `cacheQuestion` + `upsertRankings`  

### 阶段 B：工程化（1 个月）

1. **Spring Cloud Gateway** 或 Nginx 统一入口 `/api`  
2. 三服务 **Dockerfile** + `docker compose up` 含 Java  
3. GitHub Actions：`mvn test` + 前端 `npm run build`  
4. 统一 `common` 模块的 `ApiResponse`、全局异常码  
5. 深度健康检查：`/actuator/health` 含 Redis、DB、Dubbo  

### 阶段 C：产品化（2～3 个月）

1. 用户登录（JWT）+ 问题/回答归属  
2. 分页、搜索、标签；热门榜可配置权重  
3. Redis **Pub/Sub** 或 Canal 做增量同步，替代 5min 全表扫  
4. 评估队列（RabbitMQ/Kafka）替代 fire-and-forget Dubbo 异步  
5. 限流、防刷（浏览量/点赞）  
6. 前端 Pinia + Vue Router，Toast 替代 alert  

### 阶段 D：研究方向（可选）

- RAG：评估时检索知识点库再调 LLM  
- 多模型路由（千问/DeepSeek/本地 Ollama）  
- 排行榜 A/B：纯 Redis vs ES 全文 vs 协同过滤

## 六、个人感受与建议（给吕宇轩）

### 6.1 我看到的成长轨迹

这个项目不是「单点 Demo」，而是 **第九周微服务 → 第十一周 Redis → SkyWalking 可观测 → 完整报告** 的一条线。很多人 Redis 作业只会 `SET/GET` 或抄一个 ZSET；你做了 **ZSET 双榜 + 详情缓存 + 评估读缓存 + 写穿 + 定时对齐 + 级联删除**，并且能用截图和 Trace 证明「真的跑过」——这在课程语境里属于 **上游水平**。

同时，项目也典型地暴露了「赶实验 deadline」的痕迹：README 没跟上、测试欠账、报告个别表述与代码有 5% 偏差。这正常，不代表做得差，而是 **下一步该还的技术债清单**。

### 6.2 答辩建议（若被问到）

| 可能问题 | 建议答法 |
|----------|----------|
| 为什么浏览量先写 MySQL？ | MySQL 权威，Redis 加速读；重启 Redis 不丢计数 |
| 5 分钟全量同步会不会慢？ | 实验数据量小；生产可改增量或 MQ 失效，报告 §五 已承认折中 |
| 自设计场景为什么选评估缓存？ | 评估在独立库、读多写少、JSON 大、LLM 结果不变，TTL 10min 合适 |
| 和 Memcached 比？ | Redis 支持 ZSET 排行榜 + 丰富数据结构，一门课内统一技术栈 |
| SkyWalking 和健康检查区别？ | health 是存活探针 ~3ms；Trace 是单次业务链路 ~2s |

### 6.3 提交后立刻做的 3 件事

1. **轮换 DashScope API Key**（若曾在对话/截图/误打包中暴露）  
2. 本地 `npm install`（打包删过 node_modules）  
3. 把 PDF + zip 备份一份到 U 盘/网盘  

### 6.4 若只选一件事继续投入

**补 Redis 集成测试。**  
理由：实验核心是 Redis；几个 Testcontainers 用例比再加一个 UI 功能更能证明你「真懂同步策略」，对保研/求职面试也更有说服力。
